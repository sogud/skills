# Update Workspace Harness

目标是让不了解当前对话的 Agent 能从真实入口选对上下文和工具，取得可核验结果，并在失败后回到正确步骤。正确性不能用少读资料、少跑检查交换；效率看完整任务的上下文、调用、等待、返工和人工操作。

## 从纠错中改进

用户明确要求保存教训或优化长期行为时，按以下步骤处理；普通任务结束、一次报错或用户表达不满，不自动启动长期写入。

1. **先解决当前问题**：按当前任务授权修复并验证；若尚未解决，说明阻塞，不先写一条规则当作修复完成。
2. **判断可复用性**：区分用户明确确认的偏好、已验证的方法和 Agent 自己的猜测。一次性要求只在当前任务生效；重复次数、赞许或沉默不能替代确认，也不能证明方法正确。
3. **提取最小教训**：说明适用条件、原来的具体错误、已验证的改法和成功检查。只保存会改变未来动作的内容，不复制聊天、逐次纠错日志或未验证归因；需改变适用范围或权限时先询问。
4. **更新唯一正文**：按下文分类、收益比较与保存位置更新现有内容。个人长期偏好按目标工作区的记忆约定保存，项目教训留在所属项目，执行规则或流程更新对应 AGENTS 或 Skill；私密内容遵循原有加密边界。
5. **检查未来行为**：用一个应适用的请求和一个不应适用的反例核对范围，并验证受影响的引用或动作。没有可验证收益就不保存；规则是否失效以事实、条件变化和用户新指令判断，不按使用频率或闲置天数自动升级、降级。

沿用现有正文和按需读取方式，不另建 self-improving 记忆目录、计数表、每次任务前后的固定加载步骤或定时复盘。

## 分类缺口

| 类型 | 识别方式 | 最小改动 |
| --- | --- | --- |
| Routing | 入口加载过多、漏触发或走错 skill / 文档 | 收窄触发，补回退，不复制正文 |
| Knowledge | 缺稳定事实、边界、术语或证据入口 | 更新唯一知识正文和必要索引 |
| Action | 已知输入能用固定步骤完成 | skill、CLI、script 或 validator |
| Loop | 目标需要“执行 → 检查 → 修复/重试” | 明确状态、检查器、回边和停止条件 |
| Workflow | 有稳定分支、并行、汇合或角色交接 | 明确节点、边、共享状态和人工操作 |
| Graph Engineering | 多个 Loop 要互相检查目标、方法、指标或结果 | 增加监督关系、真实锚点和独立判断 |

不要把一次失败当成 Loop，也不要把线性任务包装成 Workflow 或 Graph。

只有任务已分类为 Loop、Workflow、Graph Engineering，或需要评估工作区整体结构时，才读取 [Harness 结构设计](references/structure-design.md)。

## 判断是否更新

先从真实请求或失败案例拆出：已确认事实、待判断分支、状态变化动作、独立检查和需要长期复用的状态。优先删除重复读取、重复查询和无效转述。

变更前简短比较，无需另存文件：

| 维度 | 更新前 | 更新后预期 |
| --- | --- | --- |
| 完整路径 | 入口、动作、验证和返工在哪里 | 删除、合并、按需读取或复用什么 |
| 正确性 | 缺什么证据，冲突时如何处理 | 事实来源、优先级、停止条件和独立检查 |
| 上下文 | 无条件加载和按需读取什么 | 是否减少重复正文和无关内容 |
| 操作次数 | 重复调用、构建、验证或人工确认 | 怎样复用仍有效的状态和证据 |
| 下游影响 | 当前改动会转移什么成本或风险 | 需求、实现、验证、交付和维护是否都受益 |

仅在同时满足以下条件时更新：

1. **正确性不下降**：新增事实来自源码、运行时、权威文档或用户明确确认；证据过期、缺失或冲突时重新核验或停止。
2. **有可验证收益**：减少读取、调用、等待、返工或人工操作，或以低成本检查避免明显的高成本失败。
3. **不增加无关上下文**：长期入口只放强制约束和路由；细节按任务读取；同一正文不复制。
4. **不制造重复动作**：仍有效的证据不重跑；有效性同时考虑相关源码、依赖、配置、产物、运行环境、Case 和时间窗口。写入超时或响应丢失时先查真实状态，禁止盲目重试。
5. **不做局部优化**：不能只让某一步更快，却提高误改、漏验、误发布或维护成本。

没有整体收益就明确决定不更新。不要保存一次性日志、临时快照、未验证猜测、密钥或账号信息。

## 追踪真实路径

不要从预想文件直接开始修改。

1. 用真实请求或失败案例描述期望行为。
2. 先读目标工作区的 `AGENTS.md`、README、配置、现有 skill description 或索引，再沿 Agent 实际可见路径前进。
3. 检查“触发 → 上下文 → 动作 → 验证 → 失败处理 → 长期保存”是否完整。
4. 按上表分类缺口，确认唯一正文和最小修改范围。
5. 如果关键步骤仍依赖当前对话、Agent 常识或“应该能想到”，补充对应的入口、正文或确定性工具。

优先遵循目标工作区的目录和 Git 规则。需求状态、任务过程、运行产物和历史记录分别保存到该工作区已规定的事实源；不要新建第二套状态文件或把它们混进通用知识。

## 选择唯一正文

按目标工作区现有约定选择位置。通常：

| 内容 | 唯一正文 |
| --- | --- |
| 长期红线、必读项和技能路由 | `AGENTS.md` |
| 稳定业务、架构和工程知识 | `docs/` OKF bundle |
| 单个技能的流程和工具约束 | 对应 skill 目录 |
| 确定性、重复的动作或判定 | script、Hook 或 validator |
| 需求、设计、任务和验收状态 | 工作区既有的需求状态源 |
| 仓库路径、remote 和所有权 | 工作区既有仓库清单 |
| 可重建日志、截图和原始抓取 | 工作区的 artifact 目录 |

其他位置只保留触发条件和链接。判定算法归其 validator 或脚本；流程 skill 只说明何时调用、怎样解释结果、失败后回到哪里。

更新 `docs/` 前读取 [OKF 文档约定](references/okf-docs.md)。目标工作区已声明其它格式时，以其明确规则为准。

## 文档维护纪律

知识沉淀的价值取决于「被检索命中」，而关键字检索的命中率取决于文档里是否写了使用者实际会搜的词。维护比新增更重要：

- **术语和别名进术语表**：正式名、缩写、别名、入口名、中英文变体都收录。检索词没命中时，优先回补对应别名到术语表，而不是新建文档或引入语义检索工具。
- **检索关键词显式化**：错误码、API 名、注解名、仓库名、平台名在正文或表格中原样出现，不改写、不意译；报错文案里的关键片段值得作为检索词保留。
- **索引类文档与源头同步**：接口清单、埋点索引、仓库索引、关系图谱等索引类文档，在对应源码或平台配置变更的同一任务内更新；无法同步时标注快照时间。过期索引比没有索引更糟。
- **路由 miss 即回补**：发现 Agent 需要全库 grep 才找到某知识，说明路由表或术语表缺条目，当次补上。

## 执行与验证

1. 明确事实/失败信号、证据、复用场景和完成标准。
2. 比较更新前后完整路径；不满足收益条件则停止。
3. 只修改入口、唯一正文、执行能力和验证中必要的最小集合。
4. 校验修改后的触发、链接、结构、脚本或配置；有文件改动时运行 `git diff --check`。
5. 用一个正向请求和一条相似但不应触发的反例检查路由。对 Loop 还要检查通过条件、失败回边、重试上限和最终停止；对 Workflow 检查节点契约、并行写入隔离、汇合和人工确认。
6. 再比较完整路径；产生额外读取、重复操作、歧义或下游风险时缩小或撤回改动。

需要独立验证时，只提供 skill 路径、原始材料和自然用户请求；不要泄露预期答案或本次改动意图。

最终汇报实际改动、可观察的行为或效率变化、验证结果和剩余问题；没有实测数据时明确区分预期与事实。
